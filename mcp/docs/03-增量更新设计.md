# 03 · 增量更新设计（调研结论与实施路线）

> 回答两个问题：① 本次静态方案如何低成本迭代；② 哪些环节必须 LLM、哪些可以纯程序。所有设计决策都以 01 文档的运行数据和 02 文档的能力盘点为依据，不引入新算法。

## 1. 设计原则

1. **确定性进 MCP，判断留 LLM**：凡是"有命令能决定"的环节（搜索、评分、对账、差异检测）做成工具；凡是"需要 meta 知识或权衡"的环节（队伍设计、优先级）留给 LLM。
2. **数字可复现**：任何进入方案书的实测数字必须能从一次工具调用复现（证据 = 调用参数 + 结构化返回），不接受 LLM 转述的中间值。
3. **只读红线不变**：真实存档原件零写入；服务端组合调用天然消除 LLM 触碰写类工具的风险面。
4. **增量优先**：日常迭代只重算受影响体系，不重付预检/盘点/写作的固定成本。

## 2. 程序化 vs LLM 边界（逐环节判定）

依据：本次运行中数字对账零错误、复核员抓到的 3 处问题全部是描述不一致（01 §3），说明机械核对完全可下沉。

| 环节 | 判定 | 依据 |
|---|---|---|
| 存量盘点 | **纯程序** | `extract.cjs` 已是确定性脚本；或改用 `list_characters`+`score_relics` 组合 |
| 规模闸门标定 | **纯程序** | 收紧旋钮（enhance:0 / setFilters / 主词条白名单）可从评分元数据推导，二分至 ≤2e7，≤6 轮有界循环 |
| 每队 DPS 量化 | **纯程序** | optimize / dps_score 本身是确定性工具（引擎已 153/185 项验收对拍） |
| 数字对账 | **纯程序** | "该数字在不在该 result 里"是结构化比对；本次复核员数字层零发现 |
| 零成本换装检测 | **纯程序** | 顶部行遗器 × `build.conflicts` × 库存 `equippedBy` 交叉，纯代码 |
| **机制队设计**（哪 4 人最强） | **必须 LLM** | 引擎只回答"给定队伍，装备上限多少"；"该组什么队"是 meta 知识 + 机制阅读问题，存档中无可推导数据（真珠=欢愉 BiS 不在任何数据里） |
| 缺口叙事 / 跨队优先级 | **必须 LLM** | 涉及账号目标函数的权衡；但单项 delta（升级表）已是程序产出 |
| 存量队候选提名 | **混合** | LLM 提名 2~3 候选 → 整队评分全量对拍、数字裁决（本次只对拍 1~2 个，最值得改进） |
| 方案书写作 / 试读 | **必须 LLM** | 但"数字刷新"类更新可模板化到接近零成本 |

**推论：日常迭代（刷遗器/换装/抽卡）只需要"重新打分"，零 LLM 参与；LLM 只在"队伍该不该换人"（版本更新、新角色入手）时上场。**

## 3. 双模式矩阵

| | Mode A · 数字刷新 | Mode B · 队伍重设计 |
|---|---|---|
| 触发 | 扫描器导入、换装、日常 farming | 版本更新、新角色/光锥到手、meta 变化 |
| 输入 | 队伍名单（固化在方案书） | roster 变更 + 版本知识 |
| 流程 | `plan_diff` 定受影响体系 → `team_audit` × N → 模板化更新数字表/换装清单 | LLM 重提名机制队与存量队候选 → 整队评分对拍 → 固化新名单 → 回归 Mode A |
| LLM 参与 | **零**（或发布时一段模板化文字） | 设计师 + 执笔（复核可减为抽检） |
| 预期成本 | 分钟级，接近零 token | 每受影响体系一次设计师会话 |
| 覆盖场景 | **约 90% 的迭代** | 约 10%，但决定名单本身 |

## 4. 新增工具规格

### 4.1 `team_audit`（核心）

```
输入: characterId, teammates?[3], conditionalsOverrides?,
      autoTighten=true, resultsLimit=50, enhanceFloor=0
输出: {
  status, engine, permutations: {initial, final, rejected?},
  tightenSteps?: [{overrides, perms}],          // 自动收紧轨迹
  comboNow,                                      // equippedRow.COMBO（当前 6 件）
  topRows: [{id, stats.COMBO, build, conflicts}],// 前 N 行
  comboBest,                                     // 顶部行 COMBO
  score: { percent, grade, upgrades },           // 核心 dps_score
  teammatesScores?: [{characterId, percent, grade, upgrades}],
  zeroCostSwaps: [{slot, addRelicId, removeRelicId, deltaCombo}],
  inventoryFingerprint,                          // 相关遗器库存指纹（plan_diff 用）
  timing
}
```

内部流程（全部服务端，一次 MCP 会话）：

1. 表单基准：角色已保存表单（无表单则 `default_form` 路径，**必须给 lightConeId**）；
2. 整表预处理：**删除空 `relicSets`/`ornamentSets` 内部别名**（否则反向覆盖 setFilters，见 01 §4 坑 2）、强制 `enhance: 0`（坑 1）；
3. `permutations` 估算 → `>2e7` 时按评分元数据收紧（锁 4 件套/饰品 + 主词条白名单）→ `=0` 时复用 `suggestionsEngine` 放宽，≤6 轮；
4. `optimize`（resultsLimit 行）→ equippedRow + 顶部行 + conflicts；
5. `dps_score`（核心 + 队友，team 口径统一——**队友影响 4.2 倍，见 01 §4 坑 3**）；
6. 零成本换装：顶部行逐槽与库存交叉（`equippedBy == null` 或让出损失小于收益）；
7. 指纹：参与本队搜索的遗器集合哈希。

只读：不落盘、不写表单（applyFixes 路径不进入）；`status/rejected/cancelled` 语义沿用 optimize。

### 4.2 `plan_diff`（增量触发）

```
输入: baselineFingerprints?（缺省=上次 team_audit 留存）, scope?
输出: { rosterDiff, relicsDiff, affectedTeams: [{teamKey, reason: "relicsChanged"|"rosterChanged"|"meta"}] }
```

实现：roster/遗器库存指纹对比（纯代码）；受影响体系 = 名单成员的库存指纹变化的队。**Mode A 的触发器自动化。**

### 4.3 `team_score`（可选，Mode B 用）

把 `captureTeamBenchmarkSnapshot` 暴露为对任意 4 人组打分的只读工具（不经过组队展示页槽位）。用途：LLM 提名的存量队候选全量对拍；机制队（含未持有角色）给出统一口径的整队分，替代"分析性估计"。

## 7. 风险与开放问题

1. **引擎/机制数据版本耦合**：`game_data.json`、conditionals 来自仓库代码。版本更新后必须 `git pull`（追 `beta`）→ `npm run build` → `npm --prefix mcp run build`，否则算的是旧机制。建议 plan_diff 的输出带上引擎版本指纹（mcp/dist 构建时间 + git commit），版本不符时强制全量重设计。
2. **"理论最高"的下限依赖收紧配方**：排列压得越狠，搜出的 COMBO 越可能低于真实上限（本次黄泉 3.08e6 vs 默认 1.25e9）。team_audit 应在返回里携带 `permutations.final` 与收紧轨迹，方案书标注口径——这是"理论最高"诚实性的关键。
3. **optimize 缓存只保留最近一次**：跨队审计若复用 `get_results`，需在每队 optimize 后立即消费。
4. **rate limit 对工作流墙钟的影响**：本次并发被压到 3/10。Mode A 不受影响（无 LLM）；Mode B 建议按受影响体系分批跑。
5. **整队评分的口径待验证**：`captureTeamBenchmarkSnapshot` 的评分口径（各槽位基准）与单角色 COMBO 不同，暴露为 `team_score` 前需实测其对拍行为（列入步骤 ① 的验证项）。
