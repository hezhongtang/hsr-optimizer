# 01 · 配队工作流复盘（2026-10-11）

> 对象：动态工作流「星铁配队方案·双逻辑六体系」完整运行。
> 需求原文：调用 optimizer 的 MCP，按持有角色/遗器/光锥设计多个配队（含 DoT、欢愉、追击等），给出各队理论最高 DPS 与待补足清单，且分两套逻辑（机制优先 / 存量练度优先）。

## 1. 架构与拓扑

16 个子代理、4 个阶段，一次汇合点在阶段二末尾：

| 阶段                     | 子代理                         | 职责                                                                                                                                                                                                                             |
| ------------------------ | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 预热 MCP 并盘点家底      | MCP 预检员、家底盘点员（并行） | 预检员写 `driver.cjs` + dump `tools.json` + 实测标定（规模闸门配方、队友敏感性、dps_score 耗时）→ 手册 `mcp-notes.md`；盘点员用 `extract.cjs` 从存档确定性提取 `roster.json`（60 角色）+ `relics-summary.md` + 推荐 3 个额外体系 |
| 逐体系设计配队并独立复核 | 6×（设计师 → 复核员）流水线    | 每体系产出机制队+存量队；设计师直接驱动 MCP 取实测数字；复核员只读证据目录对账                                                                                                                                                   |
| 汇总撰写配队方案书       | 方案书执笔                     | 12 队整合成书，采纳复核修正                                                                                                                                                                                                      |
| 独立试读修订并发布       | 独立读者 → 执笔修订            | 冷读挑毛病，修订后发布为工件                                                                                                                                                                                                     |

安全设计（全程有效，存档原件零写入）：

- **按次播种**：每次驱动调用把真实存档只读复制进独立 state 文件（`HSR_MCP_STATE_FILE` 的 localStorage 文件后端，键 `state` 的值 = 存档 JSON 字符串），MCP 进程永远接触不到原件；
- **只读红线**：`mcp-notes.md` §2 实测清点了全部 23 个写类工具及 3 个隐藏写入口（`optimize applyFixes`、`calc_aha save`、`warp_plan save`），设计师 prompt 内禁用；
- **确定性门禁**：脚本用 `world.run` 跑 `driver.cjs --selftest`（真实存档载入 60 角色 / 2355 遗器，exit 0），失败则提前终止不出半成品。

## 3. 质量结果

- 12 队全部产出；**4/6 队零修正通过独立复核**（黄泉/追击/欢愉/大黑塔），2 队数字全对但各带描述性修正（DoT、饮月）；
- **数字层零错误**：复核员逐字核对了所有 COMBO / dps_score / 升级表 delta 与证据文件，全部一致（容浮点尾差）；optimize 调用全部 `status=completed`、`validPermutations>0`；
- 复核员抓到的 3 类问题全部是**描述与证据不一致**，不是数字错误：
  1. "黑天鹅前 50 行**全部**含 17302" 实为 **46/50**（同条 gaps 自己引用的反例就是那 4 行之一，前后自相矛盾）；
  2. "星期日 E0 未解锁 e2DmgBuff" 实为 **E1**（roster.json 与 01-result.json 双重佐证）；
  3. notes 声称存在 `00-自检` 证据文件，目录里实际不存在（自检数字仅由 roster.json 间接佐证）。
- 独立读者提出 8 条修订（含口径表述、对比表可读性），全部采纳后发布。

## 4. 实测踩坑记录（对复用者最值钱的部分）

完整版在 `.zcode/team-plan-out/mcp-notes.md`（8 节操作手册，全部实测），此处只列影响后续设计的：

1. **`enhance` 默认下限是 9**：存档表单与 default_form 都带 `enhance: 9`，而 2355 件库存里 1922 件是 +0——按默认值锁套装会把球/绳交集清零。任何自动收紧逻辑必须显式 `enhance: 0`。
2. **内部别名反向覆盖 display 字段**：`get_form`/`default_form` 整表里带空的 `relicSets: []` / `ornamentSets: []`，作 formOverrides 用时优先于同批下发的 `setFilters`（实测：不删 → 3.26e13 排列且套装锁失效）。**这条是"permutations 通过但 optimize 拒绝"的经典成因**——自动收紧逻辑必须规范整表预处理。
3. **队友口径影响 4.2 倍**：同一角色同配方，不设队友 vs 3 辅助队友，顶部 COMBO 263,046 vs 1,102,330。任何横向对比（跨角色选主 C、跨队伍排名）必须逐字相同地设队友，否则数字不可比。
4. **`equippedRow` 不受 formOverrides 过滤**：它是当前 6 件的基线行——当收紧配方不含当前套装时，会出现"基线行 COMBO 高于榜首行"的假象（非 bug，口径问题）。
5. **规模闸门**：默认表单可达 1.25e9 排列（>5e7 必拒）；实测配方（enhance:0 + 锁 4 件套 + 饰品 + 宽主词条白名单）压到 3.08e6，optimize 50 行 9.6~13.5s（≈1e6 排列/秒）。压太狠（6,384 排列）会搜不到优于现装的解。
6. **无配装角色**：`default_form`（必须给 lightConeId）→ 删两个内部别名键 → 259,200 排列 → 3.0s 跑通，是可复现的标准配方。
7. **驱动基础设施坑**：自写客户端必须在 connect 后立即消费 stderr 管道（否则 64KB 缓冲写满死锁）；`maxBufferSize` 必须 128MB（长结果表超 10MB 默认值）；`optimize` 结果缓存服务端只保留最近一次（翻页用 `get_results`）。

## 6. 对后续设计的四点启示

1. **成本结构**：预检+执笔+读者是"基础设施/表达层"，可一次性摊销或模板化；真正的重复成本是 6 名设计师各自"学驱动 → 摸配方 → 多次冷启动"——这正是 `team_audit` 工具要消灭的部分（见 03 文档）。
2. **复核发现的价值分布**：数字全对、错全在描述——说明**数字对账应下沉为代码**，独立复核的角色应聚焦语义与建议合理性。
3. **机制队 vs 存量队的量化不对称**：存量队每个数字都有引擎实测背书；机制队中未持有角色的 DPS 只是分析性估计（dpsMeasured=false）。增量设计应把"整队评分"（`captureTeamBenchmarkSnapshot` 已在服务端存在）暴露出来，让候选队伍可以全量对拍而非凭直觉排序。
4. **一次脚本参数错误烧掉一次中止**：门禁命令应先用 snippet/本地预演验证参数形态再进脚本（本次修复只花一行 Edit + 一次缓存导入，代价可控但可避免）。
