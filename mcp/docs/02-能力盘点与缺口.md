# 02 · MCP 能力盘点与缺口（面向配队分析）

> 目的：回答"增量更新方案里，哪些能力 MCP 已经有了、缺什么、补齐的验收成本是多少"。工具清单以 `.zcode/team-plan-out/tools.json`（61 工具，2026-10-11 dump）为口径，性能数字全部来自同日真实存档实测。

## 3. 实测性能基线（2026-10-11，真实存档 60 角色 / 2355 遗器）

| 操作                                              | 实测        | 备注                                                                 |
| ------------------------------------------------- | ----------- | -------------------------------------------------------------------- |
| 驱动冷启动（播种 1.5MB + Metadata 初始化 + 连接） | 每次数秒    | 本次 46 次调用 = 46 次冷启动；**服务端内组合调用只需启动一次**       |
| `permutations`（同 formOverrides）                | 亚秒级      | 闸门估算与 optimize 同路径，`gate.wouldReject` 同口径                |
| `optimize`（3.08e6 排列，50 行）                  | 9.6~13.5s   | ≈1e6 排列/秒（CPU 6 worker）；1.25e9 排列的默认表单会被 5e7 闸门拒绝 |
| `optimize`（259,200 排列，无配装角色）            | 3.0s        |                                                                      |
| `dps_score`                                       | 0.9~1.5s/人 | 含升级表模拟                                                         |
| `describe_conditionals`                           | 亚秒级      |                                                                      |

单队完整审计（1 次 optimize + 核心+2 辅助 dps_score + 条件查询）在服务端内组合的预算约为 **15~25s**——本次每队 5~11 次冷启动调用加 LLM 往返，是它的一个数量级以上。

## 4. 缺口清单（按对增量方案的影响排序）

1. **无"单队一键审计"工具**：完整的"permutations → 收紧 → optimize → dps_score ×N → 零成本换装"目前需要 LLM 编排 5~11 次工具调用 + 现场摸收紧配方。这是本次 19.3M 设计师 tokens 的直接来源，也是结果非确定性的来源（配方选择影响排列空间，进而影响"理论最高"的下限）。
2. **无自动收紧**：5e7 闸门的规避目前靠 LLM 按 mcp-notes.md 手工配方。三个坑（enhance 默认 9、内部别名覆盖、partCounts 耦合）说明这个流程**不适合交给每次重新开始的 LLM**——它应该是确定性代码（二分/按元数据收紧，≤6 轮有界循环）。
3. **无快照差异检测**：哪些体系受"新遗器/新角色"影响，目前靠人判断。缺一个 `plan_diff` 类工具（roster/库存指纹 vs 上次审计快照 → 受影响体系清单）。
4. **整队评分未暴露为任意 4 人组打分**：`captureTeamBenchmarkSnapshot` 只服务于组队展示页槽位，不能对"假设队"直接打分——机制队候选的全量对拍因此缺一块拼图。

## 5. 新增工具的验收协议成本

仓库已有成熟协议（`mcp/coverage/`，185 features / 153 verified 基线）：

- 新工具 = `mcp/src/domains/` 新域文件（或并入 optimizer/simulation）+ features JSON 新域 + 对应 `verify-*.mjs` 验收脚本 + `coverage-check.mjs` 门禁全绿；
- 参照 M4-M9 里程碑模式，一个"组合现有引擎、无新算法"的 domain 工具（如 team_audit）的落地成本约为 **1 个 domain 文件 + 1 份 features JSON + 1 个 verify 脚本**，验收口径可直接复用现有 optimizer/scoring 证据方法（browser-parity / inprocess-parity）；
- 风险点：coverage census 会把新工具计入预算校验（features/census/工具预算），需同步 `--write` 重建 summary.md（stale 是唯一可容忍失败）。

## 6. 结论

**引擎侧没有缺算法，缺的是组装。** 整队评分、诊断建议、对比分析、闸门估算四块积木全部在服务端存在；把它们组成 `team_audit` / `plan_diff` 两个一等工具，增量更新方案（见 03 文档）就只剩薄薄的编排层。工程路径建议先走脚本验证（`mcp/scripts/team-audit.mjs`，零验收成本）再升格 domain 工具，与 M1-M9 的 smoke → tool 演进模式一致。
